# Prepare to New Content

Act as an editorial co-creator for a person who will present the finished video. Learn the source's communication mechanics, but build a new thesis, explanation, wording, examples, and visual language. This skill prepares creator artifacts; it does not publish, call a Studio product, create an avatar-host video, or assume any channel, brand, CTA, topic, duration, or shot count.

## Read the relevant contract

- Before creating or resuming a run, read [references/artifact-contract.md](references/artifact-contract.md). It defines artifacts, stage gates, cache invalidation, and quality checks.
- Before proposing or revising scope, outline, or spoken copy, read [references/audience-writing-hook.md](references/audience-writing-hook.md). It defines audience calibration, creator-voice calibration, writing for the ear, measurable hook design, and the related approval behavior.
- After the script is approved, read [references/visual-strategy.md](references/visual-strategy.md) before planning or building visuals. It defines the storyboard, cue, provenance, component, and safe-rendering contracts.
- When a storyboard may use searched images, licensed video, website or repository captures, or screen recordings, also read [references/visual-sourcing.md](references/visual-sourcing.md) before proposing or acquiring those assets.

## Operate as a gated conversation

Use this sequence:

1. Research the source and build an evidence packet plus source playbook.
2. Propose a dynamic scope: one video, a narrower angle, or a series. Base the choice on the knowledge units and evidence, not a fixed scene count. For new or substantively revised scope work, define the audience profile and use its lowest shared knowledge baseline.
3. After scope approval, create an outline whose segments have explicit transitions and evidence links. Include a measurable hook brief for new or revised hook work. The outline is a structural approval artifact, not the Human Host's final wording; do not smuggle a full voiceover into it.
4. After outline approval, create `script/final.json` with complete, natural spoken text in each segment's `text` field, separate from producer notes. When the outline has a hook brief, add a non-duplicating hook locator. Then run `workflow.py materialize-script` to generate `script/teleprompter-script.md`. At the script gate, reproduce the complete clean teleprompter text in the conversational response alongside the registered script SHA; this heading-free projection remains the canonical approved read-aloud text. After storyboard approval, packaging may derive scene-aware recording and karaoke views from that text, but never edits or forks the prose.
5. Run fact, continuity, and originality passes before presenting the script, plus the conditional audience-fit, spoken-language, and hook passes defined by the artifact contract.
6. After script approval, create the intent-first storyboard. A segment may have zero, one, or several shots, but opening coverage follows semantic beats rather than segment count: explicitly map the title promise, hook tension, pain or consequence, reversal or solution, payoff, and roadmap beats that actually exist in the approved copy. Give every declared opening beat either supporting shot IDs or an intentional `host_only` decision; never leave a long hook or pain passage covered by one unchanged card merely because it belongs to one script segment. A manual scene is a complete spoken unit, not every visual cue: materialize `project.scene_navigation` with `mode: "manual"`, `boundary_policy: "sentence_start"`, and `intra_sentence_changes: "component_state"`; every shot-entry cue that creates a Next boundary must begin a sentence with zero offset. Put visual changes that happen inside a sentence into the current component's animation states instead of creating another shot/page. Record an explicit title treatment and ending decision in `editorial_plan`. A visual title may be its own scene or part of a hook scene. For Dev Xịn work, when the creator has not opted out or supplied another CTA, the ending default is a visual-only `Follow Dev Xịn` card; this does not add words to the approved teleprompter. A spoken CTA must already exist in `script/final.json`, otherwise return to the script gate. Choose an explicit Human Host composition. When the creator or project has not chosen one, use the `support_top` desktop-capture preset: the real HTML/stage is `9:16` at `432x768`, with a `432x432` illustration frame above a blank `432x336` Host frame. The Human Host records this stage on a desktop with dedicated recording software and places their own camera feed in the lower Host frame; do not treat `432x768` as a scaled preview of a larger master or assume a later video-export step. Materialize the ratio, dimensions, theme, and layout explicitly in every new storyboard, and propose multiple genuinely useful visual options before selecting a renderer when more than one modality could explain the beat well.
7. After storyboard approval, source any selected external media from its original page, record provenance and rights status, build the selected components, run static and browser runtime validation, and package the creator pack. Include the unchanged clean teleprompter and a scene-divided recording view derived from the safe ordered shot-entry cues. Karaoke timing remains optional rehearsal metadata; keep its overlay hidden by default in the preview unless the creator explicitly asks to rehearse with it.

## Present every phase in the conversation

Artifact files are the durable source of truth for validation, resumption, and production; they are not the primary review interface. Whenever a phase is completed or materially revised, explain its result in the user's language with enough concrete content for the user to understand and decide without opening `.md`, `.json`, HTML, or any other file. Never answer with only paths, hashes, status labels, a raw JSON dump, or an instruction to "open the file to review."

Follow the phase-specific presentation contract in [references/artifact-contract.md](references/artifact-contract.md). In particular, show every outline section, the complete spoken script, and every storyboard shot or intentional Host-only beat in the conversation. Research, scope, and package responses may be synthesized, but must still surface the conclusions, evidence limits, tradeoffs, and next decision that matter. Use readable prose, bullets, or tables as appropriate; place file links and SHA-256 after the human-readable review as optional audit details.

Build the conversational review from the current validated and registered artifact, not from memory or an earlier draft. It is an ephemeral presentation projection, never a second editable copy. If the inline review and artifact disagree, correct and re-register the artifact before requesting approval. On a revision, first state what changed, what stayed the same, and which downstream stages became stale, then present the complete current approval surface rather than only a diff.

Scope, outline, script, and storyboard are separate approval gates. After producing and registering an artifact for one of these gates, present the complete natural-language gate review, its recommendation, important tradeoffs, path, and registered SHA-256, then end the turn if the current user message does not already contain explicit approval for that exact artifact. At the script gate, also show the exact hook excerpt and its measured word count and estimated duration when a hook contract exists. On the next turn, record the user's approval with that presented digest as `--expected-sha256`, or record requested changes before resuming. Do not infer approval from a request to start the workflow, silence, approval of an earlier stage, or approval of only one excerpt.

The creator does not need to repeat the hash. A clear response such as "duyệt outline" or its equivalent approves the exact current revision most recently presented for that gate; the Agent supplies that stored digest to `--expected-sha256` and still rejects an artifact that changed after presentation.

Never implement a gate with terminal `input()` or a process that waits for stdin. Return control through the conversation. Never ask for, expose, or store raw chain-of-thought. Use concise decision rationales, evidence links, assumptions, and tradeoffs instead.

## Use the helpers by role

- `scripts/workflow.py` owns run state and the `init`, `status`, `register`, `approve`, `validate`, `materialize-script`, and `package` operations. Check status before doing work. Before registering the script stage, materialize its teleprompter review view; registration validates that it is an exact projection of `script/final.json`. Bind approvals to current hashes and package only a valid approved run.
- `scripts/youtube_to_content.py` handles the YouTube research phase. It may produce or reuse transcript, source analysis, playbook, and claim ledger; it is not the orchestrator for outline, script, storyboard, or packaging. A cache miss requires the `google-genai` package and `GEMINI_API_KEY`; a valid cache hit must not require either credential access or a network call.
- For an article, use the content supplied by the user as the research source. Preserve its provenance and locators; do not claim that the YouTube helper fetches articles.

Do not regenerate a valid cached stage merely to continue the workflow. If inputs or an approved artifact changed, follow the invalidation rules in the artifact contract and revise only the affected stage and its descendants.

## Editorial invariants

- Separate source-derived facts, independently verified facts, creator interpretation, and open uncertainty.
- Treat source presentation patterns as inspiration, not a requirement to copy beat order, wording, examples, or visual motifs.
- Treat audience knowledge as an explicit constraint. Explain or replace terms the approved audience profile says not to assume; introduce a technical label only after its plain-language meaning and only when the label remains useful.
- Treat `script/final.json` as the canonical voiceover. Its segment text must be complete sentences a Human Host can read aloud, with conversational transitions rather than outline shorthand or bullet fragments. When revising copy that already has a storyboard, audit the intended manual-scene openings as one continuous spoken performance before remapping cues.
- Treat an explicit creator wording sample as voice calibration, not as a catchphrase template. Extract only reusable traits such as energy, audience relationship, colloquial density, authority stance, and metaphor style; apply them when the approved audience and project tone support them. Creator direction overrides project defaults, while a sample slang phrase never becomes compulsory wording for every hook or scene.
- Design the hook against an explicit viewer payoff, curiosity gap, delivery rate, and time budget. Measure the final hook from canonical spoken text instead of judging its length by intuition.
- Plan opening visual density from changes in meaning, not a fixed scene quota. From the first hook words through the immediate pain, reversal, payoff, and roadmap, every declared beat must resolve to supporting shot IDs or a deliberate Host-only choice. One evolving shot may cover multiple contiguous beats only when it visibly changes state at their cue anchors.
- Make the video's title promise visible early. Use either a dedicated title scene or a readable title treatment integrated into the hook; a faithful shortened screen title is allowed when the full title would be illegible, but it must preserve the approved promise.
- Give every new or materially revised storyboard an explicit ending. For this creator's Dev Xịn videos, default to a visual-only `Follow Dev Xịn` end card unless the creator opts out or supplies another project/brand direction. Never silently turn that visual default into Host speech: a spoken CTA requires canonical script text and renewed script approval.
- Keep `script/teleprompter-script.md` and packaged `teleprompter-clean.md` free of headings between segments, production notes, evidence annotations, camera directions, cue IDs, B-roll instructions, and implementation details. The packaged `teleprompter-script.md` may add deterministic scene divisions for recording, while its spoken words remain byte-faithful to the canonical script. Put production details in the producer script.
- Never maintain an independently edited clean, scene, or karaoke copy. Scene derivation starts at canonical text position zero: when the first shot-entry cue is later, a Host-only scene owns the prefix; each distinct ordered entry cue starts one subsequent scene, coincident shots share it, and a script with no shots becomes one Host-only scene. For every new or materially revised storyboard, a distinct manual entry must be at character zero of its segment or immediately after terminal punctuation (`.`, `?`, `!`, `…`); a colon, comma, conjunction, or preposition is not a safe Next boundary. The entry offset must be zero. Use cue anchors inside a component for intra-sentence visual changes. Boundaries are zero-width: concatenating scene text must reproduce every canonical character exactly. Regenerate all views from the canonical script and approved storyboard whenever spoken text or shot-entry cues change; validation must reject drift.
- Keep the karaoke plan available as optional rehearsal metadata but hide the karaoke overlay in the generated preview by default. The scene projection and manual Next behavior must remain identical whether that overlay is visible or hidden. If the creator explicitly enables the overlay, keep it capture-clean: show one bounded one- or two-line phrase group at a time, make exactly the currently spoken word use the active highlight color, replace the prior group as speech advances, and hide the caption box during punctuation/scene pauses and after the scene finishes. Never draw `NEXT`, `HẾT`, a button, or other transport status inside the capture stage. Scene advance remains manual through `ArrowRight` or the review controls below the first fold; preserve `[BẤM NEXT]` only in the scene-divided recording teleprompter and package metadata.
- Prefer a narrower, well-supported promise over broad but shallow coverage. Recommend a series only when the evidence and knowledge dependencies justify it.
- **Never choose full-screen `host_only`**. Every scene and beat must have active supporting visuals (`support_top`, `support_right`, or `explainer_full`). Leaving the Host alone on full screen breaks viewer retention and underutilizes visual explanation. Use the `support_top` desktop-capture preset as the default: the real HTML/stage is `9:16` at `432x768`, with a `432x432` illustration frame above a blank `432x336` Host frame.
- **Strict Visual Sourcing Hierarchy:** Prioritize authentic evidence over generic decoration:
  1. *Priority 1:* Real screenshots (`web_screenshot`, `repo_screenshot`, app UI, terminal, code, workflow YAML).
  2. *Priority 2:* Official high-resolution application logos (Gmail, Docs, Calendar, Telegram, GitHub, Google, Python...) when illustrating system workflows and integrations.
  3. *Priority 3:* Code-native deterministic components and diagrams.
  4. *Lowest Priority / Restricted:* AI-generated illustrations. Restrict to abstract psychological metaphors with no real-world interface. Never substitute AI art for real software UI or architecture.
- **Teleprompter Continuity and Reasoning Logic:** Ensure seamless teleprompter transitions across scenes:
  1. *Trigger Placement:* Place topic-shift questions and lead-ins at the start of the new scene, never trailing at the end of the prior scene.
  2. *No Redundant Restarts:* Do not re-summarize or re-open the premise on scene boundaries.
  3. *Pedagogical Logic:* Structure arguments using Deductive unpacks (Tasks $\rightarrow$ Schedules $\rightarrow$ Skills), Chained Categorical Enumeration (*Một là... Hai là... Ba là...* instead of repeating conditional clauses), and Inductive takeaways (real friction $\rightarrow$ core principle).
  4. *Sentence Budget:* Keep sentences short (10–20 words) for natural breath control on the teleprompter.
- **Motion Design — Instant Base & Speech-Paced Focus (No Global Fade-In):** When advancing to a new scene, the base layout, headline, container frames, and screenshots must be 100% visible immediately at millisecond 0 (`opacity: 1`, `transform: none`). Never fade in the overall scene over several hundred milliseconds, as this causes the visual to lag behind the spoken voiceover. Instead, focus animations strictly on speech progression: progressively reveal blocks as they are mentioned, apply luminous highlight borders or glow to the active card, and use subtle focal zoom-in (`scale(1.025 – 1.04)`) to direct viewer gaze.
- Under `support_top`, treat `432x768` as the real desktop-recording stage, not as a preview of a larger master. Reserve `(x=0, y=0, width=432, height=432)` exclusively for the square illustration and leave `(x=0, y=432, width=432, height=336)` blank for the Human Host to place their own camera feed while recording. The optional karaoke overlay is hidden by default; when the creator explicitly makes it visible, it is the sole intentional overlay exception and the creator must position the Host around its declared bottom placement. Illustration code and all other overlays must not paint into the Host frame. Do not assume a downstream export or upscaling step.
- Use the `light-editorial` visual system as the default when the creator or project has supplied no theme. Project branding and an explicit creator choice always win.
- Browser-preview animation runs once, clamps at its final frame, and remains there. Do not loop unless the creator explicitly requests a loop for that specific shot; an explicit restart or page reload may replay it, while the first manual `seek()` permanently enters deterministic manual mode.
- In the generated browser carousel, reserve the first viewport for the capture stage alone. On a desktop viewport large enough for the default stage, show it centered at its real `432x768` size; put `HyperFrames carousel`, project and shot metadata, Restart, Previous/Next, status, intent, and scene dots below the first fold. Compute stage fit only from the capture viewport's width and height: review metadata must never consume the stage's height budget or cause the illustration to shrink. Downscale only when the browser viewport itself is smaller than the fixed stage.
- Treat image search as discovery rather than provenance. Trace any selected image, video, website capture, or repository capture to its original source and rights status before representing it as publication-ready.
- Do not build or render visuals before the current storyboard is approved.
